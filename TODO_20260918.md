## Bug: Chat-Suche (WebDAV REPORT) scheitert nach OpenCloud-Restart

### Symptom
- Chat mit Ordner funktioniert (PROPFIND OK, Dateizugriff OK)
- Chat-Suche (WebDAV REPORT via Bleve) gibt HTTP 500
- Fehler: `search.go:56: "could not get user: error dismantling token"`
- Normale Browser-Session überlebt den OpenCloud-Restart komplett
- Neuer Browser + neue Session → Chat-Suche scheitert trotzdem
- Vor 2026-09-17 14:00: 0 dismantling-Fehler. Danach: 31+

### Gesicherte Fakten
1. Normale Browser-Session (PROPFIND, Upload, Download, UI) überlebt OpenCloud-Restart
2. Chat an sich funktioniert (Taki antwortet, PROPFIND auf public-files OK)
3. Nur die **WebDAV REPORT Suche** scheitert (Taki → WebDAV-Service direkt, pod-intern)
4. Neuer Firefox, komplett neue Session → scheitert auch → kein Token-Cache-Problem
5. Taki-Restart hilft nicht
6. `ms=1` bei 500ern → scheitert sofort bei Auth, erreicht Bleve nie

### Auth-Pfade (analysiert)

| Pfad | Auth | Funktioniert |
|---|---|---|
| Browser → Proxy → API | OIDC + Proxy setzt x-access-token | JA |
| Browser → Proxy → WebDAV PROPFIND | OIDC + Proxy | JA |
| Taki → WebDAV PROPFIND (public-files) | Basic Auth (public:share-token) | JA |
| **Taki → WebDAV REPORT (Suche)** | **x-access-token (Reva-JWT)** | **NEIN** |

### Der Suchpfad im Detail

```
Browser → /chat/token (Proxy-gated, OIDC)
  → Proxy authentifiziert User, setzt x-access-token (Reva-JWT)
  → Taki empfängt x-access-token, packt in Chat-Token

Browser → /chat-direct/ask (unprotected, skip_x_access_token)
  → Taki entpackt Chat-Token → stellt x-access-token wieder her
  → Taki ruft WebDAV REPORT auf (pod-intern, Port 9115)
  → search.go:45: t = r.Header.Get("x-access-token")
  → search.go:54: whoami(gateway, ctx, t)
  → gateway WhoAmI → DismantleToken(t) → FEHLER
```

### Gesichertes Verhalten (regressiv nachgewiesen)
- Komplett neue Web-Sitzung (neuer Browser) → Chat-Suche via DAV funktioniert sauber
- OpenCloud-Dienst-Restart → Chat-Suche bricht ab (HTTP 500, dismantling token)
- Taki-Restart hilft NICHT
- Erst eine komplett neue Browser-Session stellt die Funktion wieder her
- **Es ist ein Aktualisierungsmechanismus der nach dem Restart nicht greift**

### JWT-Analyse (Debug 2026-09-18) — DEFINITIVER FEHLER GEFUNDEN

```
[dismantle-debug] err=token signature is invalid: key is of invalid type:
  RSA-PSS verify expects *rsa.PublicKey
  tkn_len=1258 tkn_prefix="eyJhbGciOiJQUzI1NiIs" secret_len=32
```

- Token ist PS256 (RSA-PSS, vom IDP/Proxy)
- `DismantleToken` (jwt.go:119) übergibt `[]byte(m.conf.Secret)` (32 Byte HMAC-Key)
- JWT-Library erwartet `*rsa.PublicKey` für PS256 → `key is of invalid type`
- **DismantleToken kann PS256-Tokens grundsätzlich nicht validieren**
- Der Proxy setzt als x-access-token den OIDC-JWT (PS256), nicht einen Reva-JWT (HS256)
- Wenn es bei frischer Session funktioniert hat, ging die Suche über einen
  anderen Pfad der DismantleToken nicht aufruft

### Offene Frage
Der Proxy holt den Reva-JWT via `GetUserByClaims()` (account_resolver.go:257) —
das sollte immer ein HS256-Token liefern. Trotzdem sehen wir PS256 im Token
den Taki sendet. Woher kommt der PS256-Token?
Hypothese: Nach dem OpenCloud-Restart refresht der Browser das OIDC-Token
(silent refresh), aber die Chat-Komponente/Taki verwendet das alte oder falsche
Token. Der Aktualisierungsmechanismus greift nicht korrekt.

### Root Cause (identifiziert)

Das Chat-Token enthält einen eingefrorenen Reva-JWT (24h TTL). Nach einem
OpenCloud-Restart wird dieser Reva-JWT ungültig. Die Chat-Komponente refresht
das Chat-Token nur bei:
- `exp` < 5 Min. → aber exp ist 24h, noch weit weg
- HTTP 401 von Taki → aber Taki gibt 500 zurück, nicht 401

Taki akzeptiert das Chat-Token (eigenes Secret, gültig). Aber der eingebettete
Reva-JWT ist nach dem Restart ungültig. Die WebDAV-Suche scheitert mit 500.
Der 500 wird durchgereicht, kein Refresh getriggert.

Neue Browser-Session: `chatTokenState = null` → frisches Chat-Token → frischer
Reva-JWT → funktioniert.

### Fix-Plan

**1. Taki (chat.go):** Wenn die WebDAV-Suche mit Auth-Fehler scheitert
   (500 + "dismantling token"), sollte Taki HTTP 401 an den Client zurückgeben
   statt 500 durchzureichen. Damit triggert der Client einen Token-Refresh.

**2. Chat-Komponente (useChat.ts:482):** Auch bei HTTP 500 einen Token-Refresh
   versuchen (nicht nur bei 401). Defensivere Retry-Logik.

**3. JWT-Secret-Diskrepanz (ocis.yaml vs opencloud.yaml):** Angleichen — das
   ist die eigentliche Ursache warum der Reva-JWT nach dem Restart ungültig wird.

#### Was fehlt / was ist falsch:

1. **Kein Refresh bei 500:** `postChatAsk` behandelt nur 401 als Token-Fehler.
   Taki gibt 500 weiter statt 401. Der Browser refresht nicht.
   (Fix in useChat.ts committed: 0e9326e, auch 500 → Refresh)

2. **Warum scheitert DismantleToken nach Restart?**
   Der Reva-JWT ist HS256, das Secret ist persistent (opencloud.yaml unverändert
   seit Juni). Der Token müsste eigentlich validierbar sein. ABER: Im Debug sehen
   wir `jwt_prefix="eyJhbGciOiJQUzI1NiIs"` = **PS256**. Das ist NICHT der
   Reva-JWT sondern ein OIDC-JWT vom IDP.

   **Hypothese:** Bei der ersten Session holt `fetchChatToken()` den Token via
   `/chat/token` (Proxy-gated) → Proxy setzt x-access-token (Reva-JWT, HS256).
   Nach dem Restart: Irgend ein Mechanismus liefert den OIDC-Token (PS256) statt
   des Reva-JWT. Möglicherweise scheitert `GetUserByClaims` nach dem Restart
   und der Proxy fällt auf den OIDC-Token zurück.

   **ODER:** Das Debug-Log zeigt den Token der NACH dem Restart geholt wurde
   (neues Chat-Token). Dann ist die Frage: Warum liefert der Proxy nach dem
   Restart PS256 statt HS256?

3. **Grundsätzliches Design-Problem:** Das Chat-Token friert den Reva-JWT ein.
   Es gibt keinen Mechanismus der den Reva-JWT im Chat-Token aktualisiert wenn
   sich serverseitig etwas ändert (Restart, Key-Rotation). Der Browser refresht
   seinen OIDC-Token (silent refresh), aber das Chat-Token bleibt stehen.

### Initialisierung vs Update — der Unterschied

#### INITIALISIERUNG (neue Browser-Session → funktioniert)

```
1. User öffnet Browser → Login via IDP
2. IDP gibt OIDC-Token (PS256, kurzlebig ~5min)
3. Browser silent-refresh hält OIDC-Token frisch
4. Chat-Komponente startet:
   a) fetchChatToken() → GET /chat/token
   b) Request geht durch Proxy (OIDC-gated)
   c) Proxy: OIDC-Token validieren → GetUserByClaims() → MintToken()
   d) Proxy setzt x-access-token = FRISCHER Reva-JWT (HS256, 24h)
   e) Taki empfängt x-access-token → packt Reva-JWT ins Chat-Token
5. Chat-Request:
   a) POST /chat-direct/ask mit Chat-Token
   b) Taki entpackt → Reva-JWT (HS256)
   c) WebDAV REPORT mit x-access-token = Reva-JWT
   d) DismantleToken(Reva-JWT) → HS256 ✓ → OK
```

#### NACH OPENCLOUD-RESTART (bestehende Session → scheitert)

```
1. OpenCloud restartet → neuer Gateway-Prozess, neuer Token-Manager
2. Browser bemerkt nichts (silent-refresh hält OIDC-Token frisch)
3. Normale UI-Requests funktionieren:
   → gehen durch Proxy → Proxy holt FRISCHEN Reva-JWT → OK
4. Chat-Komponente:
   a) ensureChatToken() → exp noch weit weg → ALTES Chat-Token
   b) ALTES Chat-Token enthält ALTEN Reva-JWT (HS256)
   c) POST /chat-direct/ask → Taki entpackt → ALTER Reva-JWT
   d) WebDAV REPORT mit x-access-token = ALTER Reva-JWT
   e) DismantleToken(ALTER Reva-JWT) → ??? → FEHLER

   ODER bei Token-Refresh (500-Retry oder exp-Ablauf):
   a) fetchChatToken() → GET /chat/token
   b) Proxy: OIDC validieren → GetUserByClaims() → MintToken()
   c) NEUER Reva-JWT (HS256, 24h)
   d) Taki packt ins Chat-Token
   e) NEUER Chat-Request → WebDAV REPORT → DismantleToken
   f) → ??? → FEHLER (auch mit FRISCHEM Token!)
```

**Das Debug-Log zeigt: jwt_prefix="eyJhbGciOiJQUzI1NiIs" (PS256)**
**Aber MintToken erzeugt HS256.**

Also kommt der Token den Taki sieht NICHT aus MintToken.
Entweder:
- Der Proxy setzt nach dem Restart den OIDC-Token (PS256) als x-access-token
  statt den Reva-JWT (HS256)
- Oder GetUserByClaims scheitert und der Proxy fällt auf einen Fallback zurück

**Offene Prüfung:** Was genau gibt der Proxy nach dem Restart als x-access-token
an Taki? Ist es der OIDC-Token (PS256) oder ein Reva-JWT (HS256)?
→ Temporäres Debug-Logging in Taki handleChatToken nötig: Token-Typ loggen.
