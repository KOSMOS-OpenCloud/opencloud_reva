## Bug: jsoncs3-appauth-data Token-Blobs verloren

**Problem:** Alle 8 App-Tokens im Space `jsoncs3-appauth-data` hatten
leere Blob-Dateien (0 Bytes). Die Symlinks in `nodes/` zeigten auf
Pfade unter `nodes/` statt `blobs/`. Die `.mpk`-Dateien zeigten
`blobsize=986`/`6486`, aber die eigentlichen JSON-Daten waren weg.

**Folge:** `auth-app` konnte keine Tokens lesen → `store.Get failed: unexpected EOF`
→ Build-Worker-Auth 401 → kein Build möglich.

**Ursache:** Alte Symlinks (Altlast) zeigten direkt auf `blobs/<id>` statt
auf `nodes/<id>`. Bei UTime-Updates (alle 5 Min.) wird der Blob ersetzt →
alter Blob gelöscht → Symlink zeigt ins Leere → Token unlesbar.
Neue Symlinks (aktueller Code) zeigen korrekt auf Nodes.

Die kaputten BLOB-REF Symlinks wurden beim Container-Restart neu erzeugt
(metadatacache Retry-Loop: `initNewNode` scheitert mit `AlreadyExists`,
erzeugt dabei verwaiste 0-Byte-Nodes und -Blobs, bis zu 100 Retries).

**Fix:**
- Alle BLOB-REF Symlinks in `nodes/js/on/cs/3-/appauth-data/` gelöscht
- Frische Tokens per CLI mit `--label` für jeden Worker erstellt:
  - build-pod: `resample utility pureness aware neuron exact`
  - build-web: `oven etching quack deceiver extended entryway`
  - cloud: `provoking isotope aside unlocked urging coherent`
  - pdfa: `pulsate moistness virtual endurable essential resident`
  - steno: `vindicate grooving playtime shadow rinse uninstall`
  - witt (build-worker): `overwrite snowshoe unwary nickname union riverbank`
  - admin (job-submitter): `gloss unaired risotto despair headsman handsaw`
- Env-Dateien auf db.xwork.cloud aktualisiert
- Startscripts für alle Worker unter `/data/openworks/start-*.sh` erstellt
- Alle Worker neu gestartet, Auth OK, Pipelines registriert
- JOB_TOKEN aktualisiert (admin-Token)

**Status:** [x] Alle Worker-Tokens erneuert und funktionsfähig

## Bug: Subspace-Nutzer sehen Root-Space nicht in Space-Liste

**Problem:** User mit Leserecht auf einen Subspace (Unterordner eines Project Space)
sehen den Root-Space nicht in ihrer Space-Liste (`ListStorageSpaces`).

**Wurzelursache:** `updateIndexes()` in `spaces.go:916` returned für alle Share-Grants
(isShareGrant=true) bevor der User/Group-Space-Index aktualisiert wird.
Subspace-Grants kommen immer über die Share-API → Index wird nie geschrieben →
`ListStorageSpaces` findet den Space nicht.

**Fix (reva f1aba3f4d):**
- `spaces.go:916`: `isShareGrant(ctx)` → `isShareGrant(ctx) && nodeID == spaceID`
  Subspace-Grants (nodeID ≠ spaceID) fallen durch zu linkSpaceByUser/linkSpaceByGroup
- `grants.go:239`: RemoveGrant prüft bei Subspace-Grant-Entfernung via
  `granteeHasRemainingSubspaceGrants()` ob noch Grants in anderen Subspaces bestehen.
  Nur wenn keine mehr → Index-Eintrag entfernen.
- Neue Funktion `granteeHasRemainingSubspaceGrants()` iteriert Subspace-Liste,
  prüft Grantee-Principal auf jedem Subspace-Node.

**Status:** [x] Fix implementiert, [x] Build + Deploy (20260917-1743)

## Offen: Bleve-Suche zeigt Ergebnisse außerhalb des Subspaces

**Problem:** Subspace-User sehen in der Suche Dateinamen/Pfade/Metadaten aus dem
ganzen Space — nicht nur aus ihrem Subspace. Dateisystem-Zugriff ist korrekt
eingeschränkt, aber die Metadaten-Sichtbarkeit ist ein Datenleck.
Betrifft Bleve (Keyword) UND Qdrant (Vektor/Semantik).

**Wurzelursache:** `searchIndex()` (service.go:687) setzt für Project Spaces keinen
`searchPathPrefix`. Die Suche durchsucht den ganzen Space ohne Pfad-Einschränkung.

**Geplanter Fix (opencloud, service.go):**
1. Subspace-Only-User erkennen: `permissions.InitiateFileDownload == false`
2. Subspace-Pfade aus `space.Opaque["subspaces"]` lesen (bereits vorhanden!)
3. User-Zugang pro Subspace per Stat prüfen (einmal pro Search, nicht pro Treffer)
4. Bleve-Ergebnisse per Post-Query-Filter: nur Treffer behalten deren Pfad in einem
   erlaubten Subspace-Prefix liegt
5. Qdrant-Ergebnisse analog filtern (path-Payload)

Kein Proto-Change, kein Bleve-Umbau nötig. Performance: O(Treffer × Subspaces),
nur für Subspace-Only-User, vernachlässigbar.

**Status:** [ ] Geplant
